This guide explains the concept of Just-In-Time (JIT) user provisioning, why and when to use it, and also the instructions for configuring it.

## Overview

Just-in-Time (JIT) user provisioning allows {edition.productName} to automatically create a user account in its internal user store when a user successfully logs in using an external Identity Provider (IdP) for the first time.

This eliminates the need for manual user account creation in {edition.productName} before users can log in using external IdPs.

JIT user provisioning works follows:

1. When an application initiates an authentication request, the user gets redirected to {edition.productName}.

2. If the user selects an external IdP for authentication, {edition.productName} redirects the user to the relevant IdP.

3. If {edition.productName} receives a positive authentication response from the external IdP, JIT provisioning is triggered.

4. {edition.productName} creates a user account in its internal user store along with the user attributes obtained from the authentication response.

With this process, new user accounts are automatically provisioned to {edition.productName} when users log in with external IdPs.

## Enable JIT user provisioning

:::info[Prerequisite]
[Register the external IdP](./add-federated-login/index.mdx) as a connection in {edition.productName}.
:::

To enable JIT user provisioning for an external Identity provider:

1. On the {edition.productName} Console, click **Connections** and select the relevant connection.

2. Go to the **Just-in-Time Provisioning** tab of the selected connection.

3. Check the **Just-in-Time (JIT) User Provisioning** checkbox to enable it. Uncheck to disable it.

    <Variants><Edition only="cloud"><img src={require("../../../assets/cloud/img/guides/jit-provisioning/jit-enabled.png").default} alt="JIT user provisioning configuration is enabled" width="800" style={{display: "block", margin: "0", border: "0.3px solid lightgrey"}} /></Edition><Edition only="self-hosted"><img src={require("../../../assets/self-hosted/img/guides/jit-provisioning/jit-enabled.png").default} alt="JIT user provisioning configuration is enabled" width="800" style={{display: "block", margin: "0", border: "0.3px solid lightgrey"}} /></Edition></Variants>

4. Click **Update** to save.

:::warning
When JIT user provisioning is disabled, the following restrictions apply:

- Since {edition.productName} does not create local user accounts for federated users, those users' attributes will not be stored in {edition.productName}. Instead, attributes from the external IdP are passed directly to the application.

- If you have configured multi-factor authentication (MFA) that rely on a local user account, disabling JIT user provisioning breaks the application login flow for JIT provisioned users. Learn more about [troubleshooting sign-in flow errors with JIT](#troubleshoot-sign-in-flow-errors).
:::

## Configure JIT user provisioning settings

When JIT user provisioning is enabled, you can configure the following settings to customize how {edition.productName} provisions users.

### Attribute synchronization methods

This setting determines how {edition.productName} synchronizes user attributes between the user's account in the external IdP and the corresponding local user account.

<img src={require("../../../assets/cloud/img/guides/jit-provisioning/jit-attribute-sync.png").default} alt="Attribute Sync Methods" width="800" style={{display: "block", margin: "0", border: "0.3px solid lightgrey"}} />

- **Override All** - Overrides all attributes of the local user account with the attributes received from the external identity provider each time the user logs in.

- **None** - No attributes are synchronized. The local user account retains its attributes.

- **Preserve local** - Overrides only the attributes that are received from the identity provider. Any additional attributes that exist in the local user account but are not provided by the identity provider are preserved.

### Local account linking

This setting allows you to link federated users to existing local user accounts based on configurable rules. The rules define how {edition.productName} identifies a match between a federated user and a local user.

<img src={require("../../../assets/cloud/img/guides/jit-provisioning/jit-account-linking.png").default} alt="Account linking" width="800" style={{display: "block", margin: "0", border: "0.3px solid lightgrey"}} />

- **Enable local account linking** - Enables account linking. When enabled,
    - {edition.productName} evaluates the defined account linking rules to determine whether the federated user matches an existing local user.
    - If a match is found, the federated user is automatically linked to the corresponding local account.
    - If no rules are defined, {edition.productName} defaults to matching the email address.

- **Skip user provisioning when no local account is found** - By default, {edition.productName} creates a new local user account for the federated user if no account linking rule matches are found. This setting prevents {edition.productName} from creating a new local user account.

- **Link account if** - Configure the account linking rules. You can define a first match rule and a fallback match rule.
    - Each rule maps a federated attribute to its corresponding local attribute.
    - {edition.productName} evaluates the first match rule and if no match is found, applies the fallback match rule.
    - If none of the rules match, {edition.productName} creates a new local user account (unless the **Skip user provisioning when no local account is found** setting is enabled).

    :::tip
    Ensure you select a local user attribute that is unique for each user to guarantee accurate and consistent user matching. Learn more about [configuring unique attributes](../users/attributes/configure-unique-attributes.mdx).
    :::

</Edition>

### Preserve locally added claims of JIT provisioned users

If a user already having an account in {edition.productName} logs in using federated login with the same email address, {edition.productName} deletes any locally added claims of the user and retains only the claims provided by the federated authenticator.

If you wish to change this default behavior and preserve the locally added claims of the user, go to the `deployment.toml` file found in the `<IS_HOME>/repository/conf` directory and add the following configuration.

```toml
[authentication.jit_provisioning]
preserve_locally_added_claims = "true"
```

:::note
If an identity provider is created using the [Identity Provider REST APIs](../../reference/apis/idp/index.mdx) with the `provisioning.jit.attributeSyncMethod` property set, this will take precedence over the above configuration.
:::

## Troubleshoot sign-in flow errors

If you have disabled JIT provisioning for an IdP, applications that use [multi-factor authentication](./mfa/index.mdx) may break as certain MFA mechanisms (such as TOTP and Email OTP) require users to have local accounts in {edition.productName}.

When configuring an application's sign-in flow involving JIT-disabled IdPs and such MFA options, {edition.productName} displays the following warning:

<img src={require("../../../assets/img/guides/jit-provisioning/jit-mfa-conflict.png").default} alt="MFA based Sign-in flow with JIT user provisioning" style={{display: "block", margin: "0", border: "0.3px solid lightgrey"}} />

To avoid unexpected errors, you can use the following conditional authentication script to skip the MFA step when using JIT-disabled connectors.

```javascript
var localAuthenticator = 'LOCAL';
var onLoginRequest = function (context) {
    executeStep(1, {
        onSuccess: function (context) {
            var step = context.steps[1];
            if (step.idp == localAuthenticator) {
                executeStep(2); // MFA Step
            }
        }
    });
};
```

:::note
For more information on this script, refer to the [sign-in option-based conditional authentication script](./conditional-auth/add-adaptive-mfa/sign-in-option-based-template.mdx#how-it-works).
:::
