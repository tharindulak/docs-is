Delegation lets an application get a token for a user while preserving the identity of the party that acts on the user's behalf. {edition.productName} implements delegation with the [token exchange grant](../authentication/configure-oidc-flows/tokens-and-validation/configure-token-exchange.mdx), as defined in the [OAuth 2.0 Token Exchange specification (RFC 8693)](https://datatracker.ietf.org/doc/html/rfc8693).

The exchanged token identifies the user in the `sub` claim and the acting party in the `act` claim. When a delegated token is exchanged again, {edition.productName} nests the previous `act` claim under the new one, so a single token carries the full delegation chain.

<Edition only="self-hosted">

:::note
This feature is available from **update level 7.2.0.44** onwards. See the instructions on [updating WSO2 products](https://updates.docs.wso2.com/en/latest/).
:::

</Edition>

## Request a delegated token

Before you request a delegated token:

- Enable the token exchange grant for the application that requests the token, as described in [Enable token exchange in your app](../authentication/configure-oidc-flows/tokens-and-validation/configure-token-exchange.mdx#enable-token-exchange-in-your-app).

- Get the subject token, as described in [Token exchange flows](../authentication/configure-oidc-flows/tokens-and-validation/configure-token-exchange.mdx#token-exchange-flows). The subject token identifies the user on whose behalf the new token is issued.

- Get a JWT token for the acting user from {edition.productName}. This is the actor token.

To request a delegated token, send both tokens to the token endpoint.

{edition.productName} resolves the actor from the `sub` claim of the actor token. The request fails if the actor doesn't resolve to a user in the organization, or if the actor account is locked or disabled.

:::note[Scopes of the delegated token]
When {edition.productName} issues the subject token, it limits the scopes of the delegated token to the scopes granted to the subject token.

## The act claim

The delegated token identifies the user in the `sub` claim and the acting party in the `act.sub` claim.

The decoded delegated token looks as follows:

A resource server can use the `act` claim to record which party acted on behalf of the user, or to apply policies that depend on the acting party.

### Chained delegation

When a delegated token is exchanged again with a different actor token, the new actor becomes the current acting party, and the existing `act` claim nests under it. The most recent actor appears at the top level of the chain.

The decoded token after a second delegation looks as follows:

```json
{
  "sub": "32bc4697-ed0f-4546-8387-dcd6403e7caa",
  "act": {
    "sub": "b7e93c1a-5d48-4f2b-9a06-1c3e8f7d42b5",
    "act": {
      "sub": "2d931c9d-876e-46c0-9aba-f34501879dfc"
    }
  },
  "scope": "booking:read"
}
```

{edition.productName} carries the existing chain forward unchanged when:

- The request presents no actor token. An application that re-exchanges a delegated token can't alter the chain it received.
- The actor token identifies the user who is already the current acting party. {edition.productName} adds no duplicate level to the chain.
